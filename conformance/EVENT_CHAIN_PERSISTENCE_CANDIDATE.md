# Candidate persistence milestones 1–2

Experimental Python-only sidecar; explicitly create one dedicated database per run. Existing SDK schema and record path are unchanged. SQLite WAL with synchronous=FULL, independent connections, BEGIN IMMEDIATE writer serialization and a compare-and-update of head/count/byte count in the same transaction as the event row. No implicit creation, repair, migration, or rehashing to bless stored entries. Read snapshots are transactionally consistent and can require an independently trusted expected head/count.

Storage-specific provisional limits: 4096 entries, 2 MiB encoded storage envelope per entry, 64 MiB aggregate envelope bytes. U64 event sequences are persisted as exact JSON integers, not SQLite INTEGER. Event payload remains exact UTF-8, with no payload reserialization. The metadata JSON is only a storage envelope. Writes re-verify the entire existing chain; append is O(n) in stored entries (quadratic over a full run), not production throughput. Signed closure persistence is implemented below. Loss accounting, hostile DB schema hardening, migration, and Swift persistence are not delivered. WAL mode and process exit tests do not prove power-loss durability or malicious filesystem resistance. A consistent replacement can only be rejected using external trusted state.

Acceptance: real SQLite round-trip, explicit creation, rollback after event insertion, process exit before and after head update before commit, two concurrent connections racing the same sequence, corrupted event/head/count rejection, U64 boundary, stale checkpoint and external commitment rejection. CI lint, strict mypy and Python 3.9 tests include this module. Keep PR draft.

## Milestone 2: persistent signed closure

Separate candidate schema with explicit OPEN/CLOSED state and a singleton closure row. Older experimental sidecar schemas are deliberately rejected rather than migrated. Sign externally before seal(); a stale signed commitment must fail against the current chain under BEGIN IMMEDIATE. Trusted key ID is a mandatory out-of-band input to seal() and load_closed(). Persist context and edges (maximum 8192 edges and 2 MiB metadata), exact signature bytes and all closure commitment fields; derive the trace event array from verified stored entries. Write the closure row and CAS state in one transaction. Closed means no more append or reseal through the API. load() checks only internal consistency, including the embedded signature if closed; load_closed() requires independent trust. An attacker able to rewrite both lifecycle rows, restore an old valid database, or substitute a different valid same-key closed checkpoint is outside this local guarantee; external freshness or a retained checkpoint remains necessary. No production migration, file-system isolation or physical power-loss claim. Candidate test-only keys are never production trust roots. Tests exercise separate connections, close/append race, abrupt process exit both before and after the state update, tampering, wrong-key, stale signed close and evidence policy.
