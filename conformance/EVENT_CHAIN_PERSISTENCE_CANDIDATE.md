# Candidate persistence milestone 1

Experimental Python-only sidecar; explicitly create one dedicated database per run. Existing SDK schema and record path are unchanged. SQLite WAL with synchronous=FULL, independent connections, BEGIN IMMEDIATE writer serialization and a compare-and-update of head/count/byte count in the same transaction as the event row. No implicit creation, repair, migration, or rehashing to bless stored entries. Read snapshots are transactionally consistent and can require an independently trusted expected head/count.

Storage-specific provisional limits: 4096 entries, 2 MiB encoded storage envelope per entry, 64 MiB aggregate envelope bytes. U64 event sequences are persisted as exact JSON integers, not SQLite INTEGER. Event payload remains exact UTF-8, with no payload reserialization. The metadata JSON is only a storage envelope. Writes re-verify the entire existing chain; append is O(n) in stored entries (quadratic over a full run), not production throughput. No signed close persistence or append-after-close lifecycle, loss accounting, hostile DB schema hardening, migration, or Swift persistence is delivered. WAL mode and process exit tests do not prove power-loss durability or malicious filesystem resistance. A consistent replacement can only be rejected using external trusted state.

Acceptance: real SQLite round-trip, explicit creation, rollback after event insertion, process exit before and after head update before commit, two concurrent connections racing the same sequence, corrupted event/head/count rejection, U64 boundary, stale checkpoint and external commitment rejection. CI lint, strict mypy and Python 3.9 tests include this module. Keep PR draft.
